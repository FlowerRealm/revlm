# 插件包格式（v1）

本页是 Revlm 插件包的当前契约，即插件包格式 v1。此前没有任何已发布的格式版本，内部迭代的
旧格式记录（旧 submodule `preload-format.md`、旧 `format_version`、旧 `core_abi`/`requires`/
`targets`/`load_order`/`migrations` 字段）不属于产品状态；格式随文档迭代，因此清单不携带自
版本字段。清单中的 `abi_version` 描述的是控制面接口版本，不是包格式版本。

## 包内容

上传文件扩展名为 `.revlm-plugin`，内容是 ZIP。宿主使用 libzip 解包，不自行实现归档解析。
生产包必须同时包含 `backend/amd/` 与 `backend/arm/` 两个平台产物；每个平台目录必须恰好包含
一个可加载的 `.so`，文件名任意。其他辅助文件可以放在包内，但不能让平台目录出现第二个 `.so`。

```text
plugin.json
backend/amd/libX.so       # 平台目录即声明；文件名任意；当前平台缺失即报错
backend/arm/libX.so
frontend/entry.js          # 必须提供，可为空/no-op ESM
```

- 归档条目必须是相对 POSIX 路径，不含 `..`、绝对路径或符号链接。宿主拒绝加密条目，并对
  单文件大小与解包总大小设上限。除下列必需入口外，包可以携带任意额外文件，宿主原样保留并
  由插件自行使用。
- 校验通过后内容先写入 staging，再原子发布到 `REVLM_PLUGIN_DIR/packages/<id>/`
  （单目录覆盖，无版本目录层级）。
- 每个插件单份存在；再次安装（含更新版本）替换同一目录，不提供用户可见的版本并存或手动
  回滚。host 不保留旧包备份：新包落盘即生效，下一次冷启动迁移失败时该插件被标记 `failed`
  并按禁用处理，其余插件和服务正常启动。恢复手段是用户重新上传可用的包。

## 清单

`plugin.json` 只有六个字段：

```json
{
  "id": "Anthropic",
  "type": "channel",
  "name": "Anthropic",
  "description": "Anthropic Messages 协议插件",
  "version": "0.2.0",
  "abi_version": 1
}
```

- `id`、`version` 只含字母、数字、`-`、`_`、`.`。
- `type` 是插件类别，`channel` 表示参与渠道协议数据面；`plugin.type` 与 `ChannelGroup.type`
  是两个概念，见 [CONTEXT.md](../CONTEXT.md)。
- `abi_version` 是控制面 ABI 版本，见下节。
- 后端入口 `backend/<amd|arm>/` 与前端入口 `frontend/entry.js` 都由目录约定声明，不进入清单；
  两者都必须提供，但可以是空实现/no-op。
- 平台名固定为 `amd`/`arm`。host 只校验**当前平台**的目录，缺失即报错（安装被拒）；它不要求
  另一个平台的目录同时存在。「生产包必须同时包含两个平台产物」是对发布物的要求，由打包流程
  保证，不是安装时的门禁——否则本地只构建单架构就装不上自己的插件。
- 清单解析是严格解构：缺任一键即该插件成为失败插件，错误信息一次列出所有缺失键，宿主不为
  缺失字段静默补默认值。清单只描述插件自身，不含目录、状态或错误信息——那些是宿主运行时
  填写的，混进清单会被误报成缺键。

## ABI

接口分两层，稳定性策略不同，见 [ADR 0008](adr/0008-c-control-plane-abi.md)。

**控制面**（注册入口、模型目录登记、迁移、卸载清理）使用纯 C ABI：函数指针表与 `const char *`
承载的 JSON，不出现 C++ 标准库或第三方库类型。宿主在加载时强校验清单的 `abi_version` 与自身
控制面版本相等，不等即拒绝加载并记为失败插件。

**数据面**（协议处理器与核心服务面）使用 C++ 引用类型，插件与当前 Revlm/httplib ABI 一起冷
启动升级，错配由用户负责。这是"安装即完全信任"前提下有意接受的耦合。宿主调整数据面结构时
需要手工递增 `abi_version`——控制面版本号保护控制面，不自动覆盖数据面。

## 加载与生命周期

宿主对每个插件单独执行 `dlopen(RTLD_NOW | RTLD_LOCAL)` 并 `dlsym` 取出该插件自己的符号，不
使用 `LD_PRELOAD`，也不依赖符号插桩或 `RTLD_NEXT` 链。因此失败可以精确归因到单个插件，事务
粒度也是单个插件，插件之间不会发生符号名冲突。理由见 [ADR 0006](adr/0006-lifecycle-symbols-are-loaded-explicitly.md)
与 [ADR 0007](adr/0007-registry-replaces-symbol-interposition.md)。

生命周期入口返回 `0` 表示成功，返回非零表示失败并把原因写进 host 传入的错误缓冲区。异常不得
穿过这层边界——它是 C ABI，异常在此展开是未定义行为（[ADR 0008](adr/0008-c-control-plane-abi.md)）。
入口不带业务参数；需要访问数据库时，插件调用核心公开的数据库访问接口。

- **注册入口**：加载后立即调用一次，插件在此登记数据面路由、模型目录和普通全局端点。见下节。
- **`revlm_plugin_migrate()`**：冷启动时对每个启用插件调用；禁用插件跳过迁移，重新启用后等
  下一次冷启动执行。插件内部执行迁移 SQL 并保证幂等。安装/更新只落盘，等外部冷启动时执行
  迁移。核心 schema 先执行，插件迁移在其后。符号缺失时按 no-op 处理。一次插件迁移在单个
  数据库事务中执行；失败自动回滚本次迁移，因此不会留下半套 schema。迁移失败的插件被标记
  `failed` 并按禁用处理，不进入注册表、不加载前端；其余插件和服务正常启动，host 不因单个
  插件迁移失败拒绝服务。
- **`revlm_plugin_cleanup()`**：卸载请求只标记 pending；下一次冷启动在开始服务前加载待卸载
  插件并调用 cleanup。符号缺失时按 no-op 处理。清理失败时 host 保留包、标记 `failed`、不自动
  重试；用户再次显式发起卸载时重新调用 cleanup，成功后删除包，失败则继续保留并标记 `failed`。

插件数据库的 schema、迁移、业务数据与卸载清理全部归插件；核心不解析插件的数据库内容。

## 注册

插件在注册入口中登记三类能力。

**数据面路由**：键是方法、路径和 `ChannelGroup.type` 的三元组，值是协议处理器。路径由插件
提供，核心不预置任何前缀，因此路径形状与 OpenAI 不同的协议无需改动核心即可接入。两个插件
为不同的 `ChannelGroup.type` 服务同一路径时两者都能工作；登记完全相同的键时宿主在注册阶段
直接报错，后注册的插件成为失败插件，不按加载顺序静默取舍。

**模型目录**：按 `ChannelGroup.type` 登记。`pricing` 是插件自定义的 JSON，核心不解析。

**普通全局端点**：插件可以注册非数据面的普通端点。这类路径的冲突接受 `httplib::Server` 的
注册顺序语义，宿主不检测。

插件之间没有加载顺序规则，也没有依赖声明：注册表按键查找，与登记先后无关。供应商之间的差异
由 Channel 的 `base_url` 与 `api_key` 表达，属于数据而非代码，因此不需要"供应商插件包住协议
插件"这类依赖结构。

## 前端

`frontend/entry.js` 是普通 ESM，可为空。核心前端只动态 `import` 该模块，入口依靠模块副作用
自行挂载；host 不读取 export、不传入宿主上下文，也不提供前端 SDK。`frontend/` 下的相对资源
走同一路径前缀。

## 启用状态

启用与禁用保存在一份禁用清单里，不使用文件系统标记。文件系统是已安装包的唯一真相，不是启用
意图的载体。

清单落在 `REVLM_PLUGIN_DIR/state.json`，形如 `{"disabled": [...], "pending_uninstall": [...]}`，
写入方式是先写临时文件再改名，因此中途崩溃不会留下读起来像「没有禁用任何插件」的半截文件。
它不进核心的环境变量配置——那些是启动时只读的，而启用状态由管理端点在运行中修改；它也不进
数据库——v3 刚刚删掉 `plugin_installations` 表，为两个字符串数组把表加回来等于白删。它是一个
文件而不是一组目录标记，因此没有重建 `active/` 符号链接与 `disabled/` 标记那种重复状态。

启用与禁用即时作用于注册表：路由和模型目录立即变化，正在进行的请求不受影响。数据库迁移只在
冷启动执行，因此新启用插件的迁移等下一次冷启动。
