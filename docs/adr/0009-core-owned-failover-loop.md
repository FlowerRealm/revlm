# 核心持有失败切换循环，插件按尝试返回裁决

状态：accepted，取代 [ADR 0003](0003-api-key-owned-protocol-dispatch.md) 中候选迭代归插件的部分

候选 Channel 的轮转循环由核心持有。插件登记到路由表的协议处理器处理**一次上游尝试**，而不是整次客户端请求；它返回一个裁决，告诉核心这次结果是终局还是应当换下一个候选。

```cpp
enum class AttemptOutcome {
    Done,          // 最终结果已确定：上游成功，或不可恢复的错误
    NextCandidate, // 可恢复的失败，换下一个候选
};
```

核心的循环形状固定：取候选、调用处理器、按裁决决定继续或退出，退出后调用一次提交。轮转顺序、走到末尾回到第一个、一轮为界、退避间隔、以及「流已经开始后不再切换」都由核心实现一次。

## 理由

ADR 0003 把循环交给插件，理由是候选迭代状态不该暴露成完整列表。那个理由仍然成立，本文没有改变它：迭代器依然是核心持有的 `revlm_next_candidate`，插件依然拿不到完整候选列表。改变的只是**谁写 while**。

把 while 留在核心有两处实际收益。

一是提交点唯一。ADR 0003 的形状下提交由插件调用，因此 CONTEXT 不得不写下「插件必须自行保证不重复调用提交函数；核心不做幂等保护，重复调用可能重复落库和扣费」。这是一条把重复扣费的后果转嫁给插件作者的约束，而插件是第三方原生代码。循环回到核心之后，提交发生在循环出口的唯一一处，插件没有重复调用的接口可用，整类错误消失，不需要幂等保护也不需要那条约束。

二是轮转规则只写一遍。回到第一个候选、一轮为界、每次尝试各自受 timeout 约束、流开始后不切换——这些是产品级规则而不是协议语义。当前两个插件会各写一份，第三个插件再写一份，其中任何一份写错都表现为线上行为不一致而不是编译错误。

代价是核心变厚。这是有意接受的：循环本身约四十行，换掉的是每个插件一份的重复实现。

## 核心不判断可恢复性

B 方案的常见退化形式是核心switch上游 HTTP 状态码来决定是否重试。本文明确排除这一点，理由与 ADR 0003 一致：哪些错误可恢复是协议语义。`429` 在一个协议里是可重试的限流，在另一个协议里可能是确定性的配额耗尽；上游 `400` 的语义各家不同。核心一旦开始猜，就重新引入了它不认识的协议知识。

因此裁决由插件给出，核心只认 `Done` 与 `NextCandidate` 两个值，不读状态码、不读响应体。

## 流开始后不切换

处理器一旦把流交给核心，就不能再换候选——响应头已经确定。核心通过请求上下文自身的交接状态判断这一点，不依赖插件自觉：处理器在已交接的情况下返回 `NextCandidate` 时，核心按 `Done` 处理并记录为插件错误，而不是把半个响应接到另一个上游的输出后面。

## 流是交接，不是同步写

处理器不能同步向客户端推字节：HTTP 服务器只在请求处理函数返回之后才交出可写的 sink。因此流式响应通过 `stream_to_client(ctx, status, content_type, headers, pump)` 交接——状态行和响应头此刻确定，响应体由插件提供的 `pump` 稍后写出，SSE 分帧和 usage 提取都在 `pump` 内部，核心依然不解析。

这个时序不是要绕开的限制，它恰好就是上一节那条规则的机制：处理器还在决定是否换候选时根本拿不到 sink，所以「在已发出的响应后面接上另一个上游」在结构上不可能发生。

代价是提交点后移：交接过的请求在 `pump` 结束时提交，而不是在循环出口。仍然是一次退出、一次提交，只是晚一些。半途断掉的流因此仍会落库，记录的是处理器在断掉前累积到的 usage。

## 考虑过的方案

- 循环归插件（ADR 0003 原方案）：见上，提交点与轮转规则都被复制到每个插件里。
- 核心按 HTTP 状态码重试：把协议知识塞回核心，与「核心不认识任何协议」的前提直接冲突。
- 两套都给：接口面翻倍，`abi_version` 要保护的东西更多，而且两条路径的失败语义会随时间漂移。
