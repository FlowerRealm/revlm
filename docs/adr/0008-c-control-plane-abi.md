# 控制面用带版本的 C ABI，数据面接受 C++ ABI 绑定

状态：accepted

插件与宿主的接口分成两层，各自采用不同的稳定性策略。

控制面——注册入口、模型目录登记、迁移与卸载清理——使用纯 C ABI：函数指针表、`const char *` 承载的 JSON 参数，不出现任何 C++ 标准库或第三方库类型。插件清单声明整数 `abi_version`，宿主在加载时强校验，不相等即拒绝加载并把该插件记为失败插件。

数据面——协议处理器与核心服务面——继续使用 C++ 引用类型，插件与当前 Revlm/httplib ABI 一起冷启动升级。

## 理由

此前的设计对所有跨边界接口都使用带 C linkage 的 C++ 签名，例如接收 `std::vector<Model> &`、`httplib::Server &` 和 `const Channel &`。这些只是没有名字修饰的 C++ ABI，脆弱程度与 C++ 完全相同，却看起来安全。真实后果是可观察的：向 `Model` 增加一个字段、向 `Channel` 增加一个字段，都会让按旧布局编译的插件在运行时读到错位的内存，既不崩溃也不报错。当时唯一的防线是一个需要人工记得修改的字符串常量。

控制面的参数天然适合 C：注册的是路由键与函数指针，登记的是模型目录 JSON，生命周期入口无参数。用 C ABI 表达没有损失，换来的是一个整数版本号就能覆盖的兼容性判断，把整类静默内存破坏排除掉。

数据面不适合同样处理。协议处理器要接收 HTTP 请求与响应、要向客户端持续写出流式数据。把这些强行降级为 JSON 字符串，会在每个流式响应上引入不必要的序列化开销，而 Revlm 的主要负载正是流式代理。这里接受与 Revlm/httplib 的 C++ ABI 绑定，与“安装即完全信任、插件随宿主一起升级”的前提一致。

## 代价

存在两套稳定性规则，插件作者需要知道哪一层是哪一层。缓解方式是把它们放在不同的头文件里：控制面在一个纯 C 头文件中，数据面在 C++ 头文件中。

宿主升级数据面结构时，`abi_version` 不会自动变化，因此仍需在这类改动时手工递增它。控制面 ABI 版本保护控制面，不保护数据面。

## 考虑过的方案

- 全部使用 C ABI：数据面的流式路径要为此付出每块数据一次序列化的代价，与产品的主要负载直接冲突。
- 全部使用 C++ ABI 并配合编译期布局指纹常量：能自动检出布局变化，但把每一次核心结构调整都变成所有插件的强制重编，且指纹本身也是需要维护的机制。分层之后，控制面用一个整数就够，数据面本来就与宿主同步升级。
- 不做任何 ABI 校验：这是插件包格式 v1 最初的选择。它把错配的后果留给运行时，而错配的表现是静默内存破坏而非明确失败。
